Saya ingin melakukan SECURITY HARDENING secara menyeluruh pada project "Desa Sehat Kenanga".

PROJECT INI ADALAH WEBSITE LAYANAN KESEHATAN DESA DAN MENYIMPAN DATA SENSITIF SEPERTI:
- NIK
- Nomor KK
- Nama lengkap
- Data identitas warga
- Golongan darah
- Tekanan darah
- Gula darah
- Berat badan
- Riwayat pemeriksaan
- Data tenaga kesehatan
- Data akun pengguna
- Role dan permission pengguna

DATA TERSEBUT SANGAT SENSITIF. JANGAN MENGUBAH PROJECT MENJADI TIDAK BERFUNGSI HANYA DEMI SECURITY.

==================================================
ATURAN UTAMA
==================================================

1. JANGAN mengubah desain UI yang sudah ada kecuali memang diperlukan untuk security.
2. JANGAN menghapus fitur existing.
3. JANGAN mengubah database secara sembarangan.
4. Jangan membuat dummy security yang hanya terlihat aman tetapi sebenarnya tidak.
5. Semua perubahan harus benar-benar diterapkan pada source code.
6. Pertahankan seluruh role dan permission yang sudah ada.
7. Jangan expose data sensitif melalui frontend, API, URL, log, error message, atau browser console.
8. Jangan hardcode API key, password, token, secret, database credential, atau private key.
9. Jangan menggunakan NIK/KK sebagai identifier publik.
10. Jika menemukan vulnerability, perbaiki vulnerability tersebut, bukan hanya memberikan rekomendasi.
11. Sebelum mengubah sesuatu, pahami terlebih dahulu arsitektur project yang sudah ada.

==================================================
PHASE 2 — PERBAIKI API / JSON DATA EXPOSURE
==================================================

Ini PRIORITAS UTAMA.

Sebelumnya ditemukan kemungkinan response JSON dapat dilihat oleh user/browser.

Audit SEMUA endpoint API.

Pastikan endpoint hanya mengembalikan field yang memang dibutuhkan oleh frontend.

JANGAN melakukan:

return user;

atau:

return warga;

atau:

return pemeriksaan;

jika object tersebut mengandung field sensitif.

Gunakan explicit response/resource/DTO/serializer.

Contoh konsep:

return {
    id,
    name,
    role
}

bukan seluruh database object.

Untuk data sensitif seperti:

- NIK
- KK
- tanggal lahir
- alamat
- nomor telepon
- data kesehatan

jangan dikirim ke frontend jika tidak diperlukan.

Jika frontend memang membutuhkan data tersebut, pastikan endpoint memiliki:

1. Authentication
2. Authorization
3. Role checking
4. Ownership checking
5. Field-level access control

Contoh:

WARGA hanya boleh melihat data miliknya sendiri.

NAKES hanya boleh melihat warga yang memang berada dalam kewenangan pemeriksaannya.

ADMIN memiliki akses administratif sesuai permission.

Jangan hanya mengandalkan:

GET /users/123

lalu percaya bahwa user ID 123 boleh dilihat oleh siapa saja.

Implementasikan server-side authorization.

Jangan pernah mengandalkan proteksi frontend seperti:

if (role === "admin")

sebagai satu-satunya security.

Semua permission wajib divalidasi di backend.

==================================================
PHASE 3 — IDOR / BOLA PROTECTION
==================================================

Cari seluruh endpoint yang menggunakan:

/users/:id
/warga/:id
/pemeriksaan/:id
/health/:id
/profile/:id
/documents/:id
dan endpoint sejenis.

Test apakah user A bisa mengganti ID menjadi ID user B dan mendapatkan data user B.

Contoh:

/api/warga/123

menjadi:

/api/warga/124

HARUS ditolak jika user tidak memiliki permission.

Gunakan authorization berbasis:

- authenticated user
- ownership
- role
- permission
- relationship

bukan hanya berdasarkan keberadaan ID.

==================================================
PHASE 4 — DATA SENSITIF NIK & KK
==================================================

Karena NIK dan KK merupakan data yang sangat sensitif:

1. Jangan tampilkan NIK/KK secara penuh di UI kecuali benar-benar diperlukan.
2. Masking untuk tampilan umum.

Contoh:

327xxxxxxxxxxxxx

atau:

3273************

3. Jangan gunakan NIK/KK sebagai public ID.
4. Jangan gunakan NIK/KK dalam URL.
5. Jangan masukkan NIK/KK ke QR code secara langsung.
6. Jangan masukkan NIK/KK ke frontend JavaScript jika tidak diperlukan.
7. Jangan masukkan NIK/KK ke console.log().
8. Jangan masukkan NIK/KK ke analytics/tracking.
9. Jangan masukkan NIK/KK ke error message.
10. Jangan masukkan NIK/KK ke log aplikasi secara plaintext.

Jika database membutuhkan pencarian berdasarkan NIK:

- gunakan mekanisme yang aman untuk lookup,
- pertimbangkan encrypted storage,
- gunakan deterministic lookup strategy hanya jika memang diperlukan,
- jangan mengorbankan keamanan hanya demi kemudahan query.

Jangan melakukan hashing NIK secara sembarangan jika aplikasi masih membutuhkan kemampuan untuk mengambil kembali NIK asli.

Jika memungkinkan, gunakan encryption at rest untuk data sensitif.

==================================================
PHASE 5 — AUTHENTICATION SECURITY
==================================================

Audit sistem login.

Pastikan:

- Password tidak pernah disimpan plaintext.
- Password menggunakan hashing yang aman.
- Session/token aman.
- Session memiliki expiration.
- Logout benar-benar invalidasi session/token.
- Cookie menggunakan HttpOnly jika menggunakan cookie authentication.
- Cookie menggunakan Secure pada HTTPS.
- SameSite dikonfigurasi dengan benar.
- Jangan simpan credential sensitif di localStorage jika tidak diperlukan.
- Google OAuth callback harus divalidasi.
- Jangan percaya data role dari frontend.
- Role harus berasal dari backend/database yang terpercaya.
- Jangan memungkinkan user biasa mengubah role menjadi admin/nakes melalui request manipulation.

Pastikan juga:

- brute-force protection
- login rate limiting
- suspicious repeated login protection
- account enumeration protection jika relevan

==================================================
PHASE 6 — AUTHORIZATION ROLE
==================================================

Project memiliki beberapa tier/role.

JANGAN mengubah struktur role existing.

Audit setiap role:

- Warga
- Nakes
- Admin
- dan role/tier lainnya yang sudah ada di project

Buat matrix permission berdasarkan role yang benar-benar digunakan project.

Pastikan:

WARGA:
- hanya dapat mengakses data miliknya sendiri
- tidak dapat mengakses data warga lain
- tidak dapat mengubah data pemeriksaan milik warga lain
- tidak dapat mengakses endpoint admin
- tidak dapat mengakses endpoint nakes

NAKES:
- hanya dapat mengakses fungsi sesuai kewenangan
- tidak dapat mengakses fungsi admin
- tidak dapat menaikkan role dirinya sendiri
- tidak dapat mengubah permission dirinya sendiri

ADMIN:
- memiliki akses administratif sesuai kebutuhan aplikasi
- endpoint sensitif tetap harus memiliki authorization

Jangan mengandalkan hidden button di frontend sebagai security.

==================================================
PHASE 8 — XSS / SCRIPT INJECTION
==================================================

Saya ingin mencegah script injection terutama karena website dapat berpotensi menggunakan external scripts atau konten pihak ketiga.

Audit semua tempat yang menampilkan input user.

Jangan menggunakan:

dangerouslySetInnerHTML

atau mekanisme HTML injection lainnya tanpa alasan yang benar-benar diperlukan.

Jika memang diperlukan:

- sanitize HTML
- gunakan allowlist tag
- gunakan allowlist attribute
- jangan mengizinkan script
- jangan mengizinkan event handler seperti onclick
- jangan mengizinkan javascript: URL

Pastikan input seperti:

<script>alert(1)</script>

tidak pernah dieksekusi.

Test juga payload seperti:

<img src=x onerror=alert(1)>

<svg onload=alert(1)>

javascript:alert(1)

dan variasi encoded payload.

Jika ada user-generated content, pastikan output encoding diterapkan sesuai konteks.

==================================================
PHASE 9 — CONTENT SECURITY POLICY
==================================================

Implementasikan Content Security Policy yang sesuai dengan aplikasi.

Gunakan CSP untuk membatasi:

- script-src
- style-src
- img-src
- font-src
- connect-src
- frame-src
- object-src
- base-uri
- form-action

Jangan langsung menggunakan:

script-src 'unsafe-inline' *

tanpa alasan.

Hindari wildcard yang terlalu permisif.

Jika project menggunakan external service tertentu, whitelist hanya domain yang benar-benar diperlukan.

Tujuan:

Jika terdapat script injection, browser tetap memiliki lapisan perlindungan tambahan.

Tambahkan security headers yang sesuai.

- Content-Security-Policy
- Strict-Transport-Security

- Referrer-Policy

- frame-ancestors melalui CSP

Jangan menambahkan header yang sudah deprecated hanya demi checklist.

Jika menggunakan Nginx/reverse proxy, pastikan konfigurasi tidak bertentangan dengan backend.

==================================================
PHASE 11 — CORS
==================================================

Audit CORS.

Jangan menggunakan:

Access-Control-Allow-Origin: *

untuk endpoint yang membutuhkan authentication atau membawa data sensitif.

Gunakan whitelist origin yang memang diperlukan.

Pastikan:

- credentials
- allowed methods
- allowed headers

dikonfigurasi dengan benar.

Jangan mengizinkan arbitrary origin.

==================================================
PHASE 12 — CSRF
==================================================

Jika authentication menggunakan cookie/session:

implementasikan CSRF protection untuk request yang mengubah state.

Audit:

POST
PUT
PATCH
DELETE

Pastikan endpoint sensitif tidak dapat dipanggil oleh website pihak lain secara tidak sah.

==================================================
PHASE 13 — RATE LIMITING
==================================================

Tambahkan rate limit pada endpoint sensitif seperti:

- login
- register
- forgot password
- OTP jika ada
- Google authentication callback jika relevan
- API sensitif
- scan/QR verification
- invitation
- email sending
- account deletion
- data export

Jangan membuat rate limit terlalu ketat sehingga mengganggu penggunaan normal.

Gunakan konfigurasi yang masuk akal dan dapat disesuaikan melalui environment/config.

==================================================
PHASE 14 — QR CODE SECURITY
==================================================

Project menggunakan QR code.

Pastikan QR code TIDAK berisi:

- NIK plaintext
- KK plaintext
- password
- access token permanen
- data kesehatan

Jika QR digunakan sebagai identifier:

gunakan opaque random identifier/token.

Token harus:

- sulit ditebak
- memiliki entropy tinggi
- memiliki expiration jika memang diperlukan
- dapat direvoke
- tidak mengandung informasi pribadi

Jangan menggunakan:

QR = NIK

atau:

QR = user_id sederhana

==================================================
PHASE 16 — DATABASE SECURITY
==================================================

Audit query database.

Pastikan semua query menggunakan parameter binding / ORM yang aman.

Cari kemungkinan SQL Injection.

Jangan membuat query seperti:

"SELECT * FROM users WHERE name = '" + input + "'"

Pastikan menggunakan ORM/query builder/parameterized query.

Audit juga:

- mass assignment
- model fillable/guarded
- database permissions
- exposed database port
- production database credentials
- backup security

==================================================
PHASE 17 — ERROR HANDLING
==================================================

JANGAN expose error internal kepada user.

Production response TIDAK BOLEH mengandung:

- stack trace
- SQL query
- database credential
- file path server
- framework debug information
- environment variables
- internal exception details

Contoh buruk:

SQLSTATE...
/var/www/project/app/...
DATABASE_PASSWORD=...
GEMINI_API_KEY=...

Gunakan generic error response.

Contoh:

{
  "message": "Terjadi kesalahan pada server."
}

Detail hanya dicatat secara aman di server log jika diperlukan.

PHASE 21 — PRODUCTION SECURITY
==================================================

Pastikan production:

- DEBUG disabled
- source map dipertimbangkan sesuai kebutuhan
- HTTPS digunakan
- database tidak terbuka ke public internet jika tidak diperlukan
- Redis tidak terbuka ke public internet
- admin endpoint terlindungi
- server error tidak expose informasi internal
- directory listing disabled
- unnecessary ports disabled

Jika menggunakan Docker:

audit Dockerfile dan docker-compose.

Pastikan:

- tidak menjalankan container sebagai root jika tidak diperlukan
- tidak memasukkan secret ke image
- tidak expose port database secara publik jika tidak diperlukan
- gunakan minimal base image jika memungkinkan
- jangan menyimpan credential di Dockerfile

==================================================
PHASE 22 — FRONTEND SECURITY
==================================================

Audit frontend.

Pastikan:

- tidak ada sensitive data yang tersimpan di localStorage tanpa alasan
- tidak ada API key secret di bundle
- tidak ada NIK/KK di URL
- tidak ada sensitive data di query string
- tidak ada sensitive data di browser console
- tidak menggunakan unsafe HTML rendering
- API error tidak menampilkan internal error
- UI permission bukan satu-satunya security layer

Jika frontend membutuhkan data sensitif:

pastikan backend hanya memberikan data yang benar-benar diperlukan.

==================================================
PHASE 23 — ACCOUNT DELETION & LOGOUT
==================================================

Audit logout.

Logout harus:

- invalidate session/token
- clear authentication state
- clear secure cookies sesuai mekanisme authentication
- tidak dapat digunakan kembali setelah logout

Untuk account deletion:

- harus membutuhkan authorization
- jangan dapat dilakukan oleh user lain
- gunakan confirmation
- gunakan re-authentication jika diperlukan untuk tindakan sensitif
- jangan expose data account yang dihapus

Animasi logout boleh tetap dipertahankan karena ini bagian UI.

Namun animasi TIDAK BOLEH menjadi satu-satunya proses logout.

==================================================
PHASE 28 — SECURITY REPORT
==================================================

Setelah selesai, buat laporan dalam bentuk:

SECURITY AUDIT RESULT

1. CRITICAL
2. HIGH
3. MEDIUM
4. LOW
5. INFO

Untuk setiap vulnerability:

- Nama vulnerability
- Lokasi file
- Endpoint terkait
- Risiko
- Penyebab
- Perbaikan yang dilakukan
- Cara melakukan testing
- Status

Contoh:

[HIGH]
Sensitive Data Exposure

Location:
GET /api/warga/:id

Problem:
Endpoint mengembalikan seluruh object warga termasuk NIK dan KK.

Fix:
Menggunakan explicit API Resource dan field-level authorization.

Status:
FIXED

==================================================
FINAL REQUIREMENT
==================================================

JANGAN hanya membuat laporan.

Lakukan perubahan nyata pada source code.

Urutan kerja:

1. Audit
2. Identifikasi vulnerability
3. Prioritaskan vulnerability
4. Implementasikan fix
5. Test
6. Regression test
7. Audit ulang
8. Buat security report

Jika menemukan security issue yang berpotensi menyebabkan kebocoran NIK/KK/data kesehatan, prioritaskan issue tersebut terlebih dahulu.

JANGAN menghapus fitur hanya karena sulit diamankan.

Jika suatu fitur memang memiliki desain yang tidak aman, ubah implementasinya menjadi lebih aman sambil mempertahankan fungsi utamanya.

Terakhir, tampilkan:

- daftar file yang diubah
- daftar endpoint yang diperbaiki
- daftar security issue yang ditemukan
- daftar security issue yang sudah FIXED
- daftar issue yang masih membutuhkan konfigurasi server/deployment
- hasil security test
- potensi breaking change
- rekomendasi lanjutan

Jangan menyatakan "aman 100%".
Nyatakan secara objektif vulnerability apa yang sudah diperbaiki dan apa yang masih perlu diperhatikan.
